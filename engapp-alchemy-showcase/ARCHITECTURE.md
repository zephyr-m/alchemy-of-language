# Архитектура EngApp

## Статус

Это принятое архитектурное решение для EngApp. Новые экраны и функции должны следовать ему. Изменение этих правил требует отдельного осознанного решения, а не локальной правки ради удобства реализации.

## Общий подход

Приложение использует облегчённый Feature-Sliced Design, Atomic Design для устройства UI и чистое доменное ядро для бизнес-правил.

- Feature-Sliced Design задаёт границы модулей и направление зависимостей.
- Atomic Design применяется внутри UI и дизайн-системы.
- Бизнес-правила реализуются чистыми TypeScript-функциями, независимыми от Vue, Pinia, роутера и хранилища.
- Сценарии пользователя оформляются как features/use cases.
- Pinia хранит общее состояние приложения, но не становится местом для всей бизнес-логики.
- Явные машины состояний управляют тренировкой и голосовым вводом.
- Доменные события используются для начисления опыта, наград и достижений.

## Источник истины для интерфейса

Существующий showcase и его визуальный язык являются источником истины для интерфейса.

Showcase должен отображать те же реальные компоненты, которые использует приложение. Нельзя копировать из showcase разметку и стили в отдельную реализацию экрана.

Правильный порядок работы:

1. Найти подходящий образец в showcase.
2. Извлечь его в переиспользуемый компонент.
3. Подключить этот компонент обратно в showcase.
4. Использовать тот же компонент в приложении.

Новый визуальный паттерн создаётся только после проверки, что существующего компонента или образца действительно нет.

## Направление зависимостей

```text
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Модуль может импортировать только слои ниже себя. Страницы не импортируют другие страницы. Features не импортируют другие features напрямую. Внешний код использует публичный API модуля через `index.ts`.

## Ответственность слоёв

### app

Запуск приложения, маршруты, layouts, providers, глобальные стили и связывание зависимостей.

### pages

Композиция полноценного экрана. Страница соединяет widgets и features, но не содержит правила обучения, формулы опыта или работу с хранилищем.

### widgets

Крупные самостоятельные блоки страниц: список этапов, дневной прогресс, нижняя навигация, блок близких к освоению слов.

### features

Действия, имеющие смысл для пользователя: начать тренировку, ответить на слово, записать произношение, забрать награду.

Feature может содержать:

```text
feature-name/
├── model/
├── ui/
├── api/
└── index.ts
```

### entities

Сущности предметной области и их правила: слово, этап обучения, тренировочная сессия, достижение, игрок.

### shared

Переиспользуемые примитивы без знаний о бизнес-сценариях EngApp: базовые UI-компоненты, утилиты, конфигурация, общая инфраструктура и ассеты.

## Atomic Design внутри UI

Atomic Design используется как модель композиции интерфейса:

```text
Атомы       Button, Badge, Input, Progress
Молекулы    StageCard, XPBadge, WordProgress
Организмы   StageList, DailyProgress, BottomNavigation
Шаблоны     AppLayout, TrainingLayout
Страницы    HomePage, DictionaryPage
```

Физические папки `atoms`, `molecules` и `organisms` создавать не обязательно. Компоненты размещаются по их бизнес-принадлежности:

- общие примитивы — `shared/ui`;
- UI сущности — `entities/<entity>/ui`;
- крупные блоки — `widgets`;
- полноценные экраны — `pages`.

## Бизнес-логика

### Чистое доменное ядро

Основные правила реализуются чистыми TypeScript-функциями. Они получают данные и возвращают новые данные и произошедшие события. Они не обращаются к Vue, Pinia, DOM, роутеру, API или локальному хранилищу.

К доменным правилам относятся:

- переход слова между четырьмя этапами;
- опускание на один этап после ошибки;
- сохранение полных прохождений;
- освоение после трёх полных прохождений;
- общий лимит в 25 активных слов;
- завершение тренировочной сессии;
- расчёт опыта и наград;
- проверка условий достижений.

Пример:

```ts
function applyAnswer(word: LearningWord, correct: boolean): AnswerResult {
  return correct ? advanceWord(word) : lowerWordStage(word)
}
```

### Use cases

Use case представляет законченное действие пользователя. Он получает необходимые данные, вызывает доменные правила, сохраняет результат и возвращает итог интерфейсу.

Примеры:

```text
startTraining()
submitAnswer()
completeWordCycle()
finishTraining()
claimReward()
```

### Состояние

- Локальное визуальное состояние остаётся в Vue-компоненте.
- Переиспользуемое реактивное поведение оформляется composable.
- Общее состояние между маршрутами хранится в Pinia.
- Формулы и доменные правила не помещаются в Pinia store.
- Компоненты не обращаются напрямую к `localStorage`, IndexedDB или API.

### Машины состояний

Состояния процесса описываются явным discriminated union вместо набора независимых boolean-флагов.

```ts
type TrainingState =
  | { status: 'question'; word: LearningWord }
  | { status: 'feedback'; word: LearningWord; correct: boolean }
  | { status: 'completed'; summary: TrainingSummary }
```

Тренировка:

```text
preparing → question → feedback → next question → completed
```

Голосовой ввод:

```text
idle → requesting-permission → recording → recognizing → result | error
```

Отдельная библиотека машины состояний пока не используется.

### Доменные события

Доменные функции могут возвращать явный список событий:

```text
word_introduced
word_advanced
word_lowered
cycle_completed
word_mastered
training_completed
streak_extended
achievement_unlocked
```

Use case явно передаёт события расчёту XP, наград и достижений. Скрытая глобальная шина событий не используется.

## Маршруты

Маршрут соответствует полноценному экрану. Правильный ответ, ошибка, запись голоса и модальное окно награды являются состояниями существующего экрана, а не отдельными маршрутами.

Layout отвечает за общую оболочку, safe area и навигацию. Отдельные маршруты могут скрывать навигацию через route metadata.

## Правила добавления компонентов

1. Перед созданием компонента проверить showcase и существующий UI.
2. Не создавать параллельную визуальную реализацию существующего паттерна.
3. Компонент остаётся рядом с первым реальным использованием.
4. В общий слой компонент переносится после появления реального повторного использования.
5. Showcase импортирует реальный компонент через его публичный API.
6. Страница не содержит доменных правил и прямой работы с хранилищем.
7. Новая абстракция должна решать существующую задачу, а не предполагаемую будущую.

## Порядок внедрения

Архитектура внедряется постепенно:

1. Сохранить рабочий showcase.
2. Выделять из него реальные UI-компоненты по мере создания экранов.
3. Сформировать `app`, `pages` и `shared` на первом экране.
4. Добавлять `widgets`, `features` и `entities` вместе с реальной функциональностью.
5. Не проводить массовую перекладку файлов без продуктовой необходимости.
